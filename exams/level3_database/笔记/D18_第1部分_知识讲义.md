## 单元一：大数据是什么——4V

**大数据**不是"数据多"这么简单，学界用 **4 个 V** 来概括它的特征：

| 特征 | 英文 | 含义 | 一句话 |
|---|---|---|---|
| **大量** | Volume | 数据规模巨大（PB、EB 级） | 存不下、算不完 |
| **高速** | Velocity | 数据产生和处理速度快（实时/流式） | 来得快，还得处理得快 |
| **多样** | Variety | 数据类型多（结构化/半结构化/非结构化）| 什么格式都有 |
| **价值** | Value | **价值密度低**（海量数据里有用信息少） | 沙子里淘金 |

⚠️ **最容易被考反的一条**：4V 里的 "Value" 指的是**价值密度低**，不是"价值高"。因为数据量太大，有用信息占比反而低，需要**挖掘**。

> 有时会补充第 5 个 V：**Veracity（真实性）**——数据可能有噪声、不准确。大纲说的是 4V，记住四个即可，多一个 V 能认出来。

## 单元二：数据的三种结构

| 类型 | 定义 | 例子 | 占比 |
|---|---|---|---|
| **结构化数据** | 有严格固定的结构，能用二维表表示 | 关系数据库里的表 | 约 10~20% |
| **半结构化数据** | 有一定结构，但不严格（有标记、可嵌套） | XML、JSON、HTML | 少部分 |
| **非结构化数据** | 没有固定结构 | 文本、图片、音频、视频、日志 | **约 80%+** |

**记忆**：**大数据里绝大多数是非结构化数据**——这也是为什么传统关系数据库搞不定，需要 Hadoop 这类新框架。

## 单元三：大数据的四种计算模式（高频考点）

| 模式 | 处理什么 | 特点 | 代表产品 |
|---|---|---|---|
| **批处理** | 历史数据（一批一批） | 高吞吐、延迟高 | **Hadoop MapReduce** |
| **流计算** | 持续到达的数据流 | 实时、低延迟 | **Storm**、Flink、Spark Streaming |
| **图计算** | 节点和边构成的关系网络 | 处理图结构 | **Pregel**、Giraph |
| **查询分析计算** | 交互式查询 | 快速响应、类 SQL | **Hive**、Impala |

**记忆口诀**：**批 Hadoop、流 Storm、图 Pregel、查 Hive**。

⚠️ **常见混淆**：
- **Spark** 常被归为"内存计算"框架，能同时做批处理和流处理——考试里如果问"流计算代表"，Storm 更典型。
- **Hive** 不是数据库，是"把 SQL 翻译成 MapReduce 任务"的**数据仓库工具**。

## 单元四：Hadoop 概览——两大核心

**Hadoop** 是 Apache 开源的**分布式存储与计算平台**。

**两大核心**：

| 核心 | 作用 | 一句话 |
|---|---|---|
| **HDFS** | Hadoop **Distributed File System**，分布式文件系统 | **存** |
| **MapReduce** | 分布式计算模型 | **算** |

后来加入了 **YARN**（资源调度），形成"HDFS + MapReduce + YARN"三件套。

**设计思想**：**用大量普通机器，靠软件容错，组成一个大集群**——不是买一台超级计算机。

## 单元五：HDFS——分布式文件系统

### 主从架构

```
            NameNode（主节点）
           /        |        \
      DataNode   DataNode   DataNode   ← 从节点，存实际数据
```

| 角色 | 职责 | 考点 |
|---|---|---|
| **NameNode** | 管理**命名空间和元数据**（文件→数据块的映射、每个块在哪些 DataNode 上） | **不存实际数据** |
| **DataNode** | **存储实际的数据块**，定期向 NameNode 汇报 | 存数据 |
| **SecondaryNameNode** | **辅助**合并 FsImage 和 EditLog | ⚠️ **不是 NameNode 的热备份**！ |

⚠️ **最经典的一个陷阱**：**SecondaryNameNode 不是"第二台 NameNode"，不能接替 NameNode 工作**。它的作用只是**定期合并**元数据文件，减轻 NameNode 启动时的压力。

### 数据块（Block）与副本

- **数据块 Block**：HDFS 把大文件**切成固定大小的块**存储
  - Hadoop 1.x 默认 **64MB**
  - Hadoop 2.x 及以上默认 **128MB**
- **副本数**：每个块默认存 **3 份**（放在不同机器上），一台坏了还有别的

**为什么切块**：一个大文件可以分散到多台机器上存，还能并行读。

### 元数据的两个文件

| 文件 | 是什么 | 比喻 |
|---|---|---|
| **FsImage** | 元数据的**持久化镜像**（某一时刻的完整快照）| 存档照片 |
| **EditLog** | **编辑日志**，记录之后对元数据的每一次修改 | 流水账 |

**启动时**：NameNode 把 FsImage 读进内存，再重放 EditLog 里的操作，恢复最新状态。

**SecondaryNameNode 的工作**：定期把 FsImage + EditLog 合并成新的 FsImage，控制 EditLog 别无限增长。

### HDFS 的适用场景

- ✅ **一次写入、多次读取**的大文件
- ✅ 高容错（副本机制）
- ❌ **不适合**大量小文件（每个文件的元数据都占 NameNode 内存）
- ❌ 不适合低延迟随机读写

## 单元六：MapReduce——分布式计算

### 核心思想：分而治之

把一个大任务**拆成很多小任务并行做**，再把结果汇总。

### 执行流程

```
输入 → Split（切分） → Map（映射） → Shuffle（洗牌：排序+分组） → Reduce（归约） → 输出
```

| 阶段 | 干什么 |
|---|---|
| **Map** | 对每个分片独立处理，输出"键值对" `(key, value)` |
| **Shuffle** | 把相同 key 的数据**排序、分组**，送到同一个 Reduce |
| **Reduce** | 对相同 key 的所有 value 做**聚合**（求和、计数等） |

### 经典例子：WordCount（词频统计）

```
输入："a b a"
Map：   (a,1) (b,1) (a,1)
Shuffle：(a,[1,1]) (b,[1])
Reduce：(a,2) (b,1)
```

**这就是"大数据版 Hello World"**，考试常拿它举例。

### 组件（注意版本差异）

| 版本 | 主节点 | 从节点 |
|---|---|---|
| **Hadoop 1.x** | **JobTracker** | **TaskTracker** |
| **Hadoop 2.x（YARN）** | **ResourceManager** | **NodeManager**（+ ApplicationMaster） |

⚠️ 大纲里可能用 **JobTracker / TaskTracker**（1.x 术语），也可能用 YARN 术语。**两套都要认识**。

### MapReduce 的局限

- 每个任务都要读写磁盘，**慢**
- 不适合**迭代计算**（机器学习、图计算）→ 所以有了 **Spark**（内存计算）

## 单元七：Hadoop 生态圈（客观题爱考"谁干什么"）

| 组件 | 作用 | 一句话 |
|---|---|---|
| **HDFS** | 分布式文件系统 | 存 |
| **MapReduce** | 分布式计算 | 算 |
| **YARN** | 资源调度 | 管资源 |
| **Hive** | 数据仓库，把 **SQL** 翻译成 MapReduce | **SQL on Hadoop** |
| **HBase** | **列族** NoSQL 数据库，基于 HDFS，支持随机读写 | 大表 |
| **Sqoop** | **关系数据库 ↔ Hadoop** 数据迁移 | 搬运工 |
| **Flume** | **日志采集**与汇聚 | 收日志 |
| **ZooKeeper** | **分布式协调**服务 | 集群管家 |
| **Pig** | 数据流处理脚本（Pig Latin） | 脚本化处理 |
| **Spark** | **内存计算**框架，比 MapReduce 快 | 新一代计算引擎 |
| **Mahout** | 机器学习算法库 | 机器学习 |

**记忆**：**存 HDFS、算 MapReduce、调度 YARN、SQL 用 Hive、随机读写 HBase、搬家 Sqoop、收日志 Flume、协调 ZooKeeper**。
