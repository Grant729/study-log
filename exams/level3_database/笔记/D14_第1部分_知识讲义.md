## 单元二：需求分析——从一段话里抓三样东西

需求通常是一段大白话。你要从中抓出**三类词**：

| 抓什么 | 长什么样 | 例子 |
|---|---|---|
| **实体** | 名词（一类东西） | 医生、病人、科室 |
| **属性** | 描述实体的名词 | 医生的"姓名、职称" |
| **联系** | 动词（谁和谁有什么关系） | 医生**诊治**病人、医生**属于**科室 |

**读需求的三步**：

1. 圈出所有**名词** → 候选实体
2. 每个实体后面跟的"编号、姓名、日期"等 → 属性
3. 圈出所有**动词/关系词** → 候选联系，再判 1:1 / 1:N / M:N

⚠️ **容易漏的**：联系自己的属性（如"诊治日期"、"成绩"）——它不属于任何一个实体，属于**联系**。

## 单元三：概念设计——画 ER 图（D13 回顾）

三要素：

| 要素 | 图形 |
|---|---|
| 实体 | 矩形 |
| 属性 | 椭圆（主键加下划线）|
| 联系 | 菱形（联系的属性连到菱形上）|

联系类型判法：**拿"一个"去数另一端能对上几个**。

---

## 单元四：逻辑设计——ER 转关系模式（D13 回顾）

**四规则**：

| 规则 | 做法 |
|---|---|
| 实体 | 一实体一张表，属性变列、键变主键 |
| **1:N** | **不建表**，把"1"端键放进"N"端当外键 |
| **M:N** | **必须单独建表**，主键 = 两端键的组合 + 联系属性 |
| **1:1** | 可合并、可单独建表 |

---

## 单元五：规范化检查（D11/D12 回顾）

转出来的表，**逐个查**：

```
1NF：属性都原子吗？
2NF：非主属性有部分依赖吗？（候选键是单属性 → 直接过）
3NF：非主属性有传递依赖吗？
```

**有病的拆法**：
- 部分依赖 → 搬"**半个键 + 它决定的属性**"
- 传递依赖 → 搬"**中间属性 + 它直接决定的属性**"

⚠️ **判断候选键的完整定义**（你 D12 的错点）：
> **能唯一确定全表所有属性，且任何真子集都不能**（超键 + 最精简）

## 单元六：物理设计——用 SQL 建表（今天的新内容）

设计好了，最后要**真的建出来**。这一步用 D4 学的 DDL。

### 建表的三条铁律

#### ① 建表顺序：**父表先建，子表后建**

外键依赖谁，谁就是父表。**先建父表，否则外键找不到引用对象**。

```
科室（父） → 医生（子，引用科室）
病人（父） → 诊治（子，引用病人和医生）
```

正确顺序：`科室 → 病人 → 医生 → 诊治`

#### ② 复合主键的写法

M:N 转出来的表，主键是**两列的组合**：

```sql
CREATE TABLE 诊治 (
  医生编号 CHAR(3),
  病历号 CHAR(4),
  诊治日期 DATE,
  诊断 VARCHAR(50),
  PRIMARY KEY (医生编号, 病历号),          -- ← 复合主键：括号里写多列
  FOREIGN KEY (医生编号) REFERENCES 医生(医生编号),
  FOREIGN KEY (病历号) REFERENCES 病人(病历号)
);
```

⚠️ **别写成两行 `PRIMARY KEY`**——一个表只能有一个主键，复合主键要写在**同一行括号里**。

#### ③ 外键的写法

```sql
FOREIGN KEY (本表列) REFERENCES 父表(父表主键)
```

**注意**：外键引用的**必须是父表的主键**（或唯一键）。

### 建完验证：故意犯规

| 犯规 | 错误码 | 说明 |
|---|---|---|
| 复合主键插入重复组合 | **1062** | 同一医生对同一病人只能有一条诊治 |
| 外键插入不存在的编号 | **1452** | 引用了"查无此人"的医生 |

这两条验证，能证明你的**约束真的生效了**。

### 删表顺序：**和建表反过来**

**先删子表，再删父表**——否则父表被外键引用，删不掉（D3 学过）。

```
DROP 诊治 → DROP 医生 → DROP 病人 → DROP 科室
```

## 单元七：完整案例——医院门诊（串一遍全流程）

### ① 需求

> 医院有多个**科室**，每个科室有科室编号、科室名。
> 每个**医生**有医生编号、姓名、职称，**属于**一个科室。
> 每个**病人**有病历号、姓名、性别。
> 一个医生可以**诊治**多个病人，一个病人可以被多个医生诊治；诊治要记录**诊治日期、诊断**。

### ② 概念设计（ER）

| 要素 | 内容 |
|---|---|
| 实体+属性 | 科室(<u>科室编号</u>, 科室名)；医生(<u>医生编号</u>, 姓名, 职称)；病人(<u>病历号</u>, 姓名, 性别) |
| 联系 | **属于**：医生 N — 1 科室；**诊治**：医生 M — N 病人（属性：诊治日期、诊断）|

### ③ 逻辑设计（转关系模式）

```
科室( 科室编号, 科室名 )
医生( 医生编号, 姓名, 职称, 科室编号 )        ← 1:N，1 端键放 N 端
病人( 病历号, 姓名, 性别 )
诊治( 医生编号, 病历号, 诊治日期, 诊断 )      ← M:N，主键 = (医生编号, 病历号)
```

### ④ 规范化检查

- 科室(科室编号, 科室名)：单属性键 → 2NF；无传递 → 3NF ✅
- 医生(医生编号, 姓名, 职称, 科室编号)：单属性键 → 2NF；3NF ✅
- 病人(病历号, 姓名, 性别)：单属性键 → 2NF；3NF ✅
- 诊治(医生编号, 病历号, 诊治日期, 诊断)：复合键，非主属性"诊治日期、诊断"完全依赖于整个键 → 2NF；无传递 → 3NF ✅

→ **四张表都合格，可以落地。**

### ⑤ 物理设计（建表 SQL）

```sql
-- 先建父表
CREATE TABLE 科室 (
  科室编号 CHAR(3) PRIMARY KEY,
  科室名 VARCHAR(20) NOT NULL
);

CREATE TABLE 病人 (
  病历号 CHAR(4) PRIMARY KEY,
  姓名 VARCHAR(20) NOT NULL,
  性别 CHAR(1)
);

-- 再建子表
CREATE TABLE 医生 (
  医生编号 CHAR(3) PRIMARY KEY,
  姓名 VARCHAR(20) NOT NULL,
  职称 VARCHAR(10),
  科室编号 CHAR(3),
  FOREIGN KEY (科室编号) REFERENCES 科室(科室编号)
);

CREATE TABLE 诊治 (
  医生编号 CHAR(3),
  病历号 CHAR(4),
  诊治日期 DATE,
  诊断 VARCHAR(50),
  PRIMARY KEY (医生编号, 病历号),
  FOREIGN KEY (医生编号) REFERENCES 医生(医生编号),
  FOREIGN KEY (病历号) REFERENCES 病人(病历号)
);
```

### 建表后插数据验证

```sql
INSERT INTO 科室 VALUES ('K01','内科'),('K02','外科');
INSERT INTO 医生 VALUES ('D01','张三','主任','K01'),('D02','李四','主治','K02'),('D03','王五','住院','K01');
INSERT INTO 病人 VALUES ('P001','赵六','男'),('P002','钱七','女');
INSERT INTO 诊治 VALUES ('D01','P001','2026-10-01','感冒'),
                        ('D01','P002','2026-10-02','胃炎'),
                        ('D02','P001','2026-10-03','骨折');
```

**联合查询**（把设计出来的表用起来）：

```sql
SELECT 病人.姓名 AS 病人, 医生.姓名 AS 医生, 诊治.诊治日期, 诊治.诊断
FROM 诊治
INNER JOIN 病人 ON 诊治.病历号 = 病人.病历号
INNER JOIN 医生 ON 诊治.医生编号 = 医生.医生编号
ORDER BY 诊治.诊治日期;
```

真实输出（本机已实测）：

```
病人 | 医生 | 诊治日期   | 诊断
赵六 | 张三 | 2026-10-01 | 感冒
钱七 | 张三 | 2026-10-02 | 胃炎
赵六 | 李四 | 2026-10-03 | 骨折
```

**按科室统计医生数**（GROUP BY 回顾）：

```sql
SELECT 科室.科室名, COUNT(医生.医生编号) AS 医生数
FROM 科室 LEFT JOIN 医生 ON 科室.科室编号 = 医生.科室编号
GROUP BY 科室.科室编号, 科室.科室名;
```

真实输出：

```
科室名 | 医生数
内科   | 2
外科   | 1
```
