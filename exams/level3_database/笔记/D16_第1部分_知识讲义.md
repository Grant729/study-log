## 单元一：触发器是什么——"会自动执行的存储过程"

### 和存储过程对比着记

| | 存储过程 | 触发器 |
|---|---|---|
| 怎么执行 | **手动 `CALL`** | **自动**（事件发生就触发）|
| 绑定在什么上 | 数据库 | **某张表的 INSERT / UPDATE / DELETE** |
| 有没有参数 | 有（IN/OUT）| 没有参数 |
| 典型用途 | 封装查询/业务逻辑 | 审计、自动维护、兜底校验 |

**一句话**：**触发器 = 绑定在表上的"自动反应"**。

**生活比喻**：存储过程像**你主动点的外卖**；触发器像**烟雾报警器**——不用你按，一有烟（事件）就自动响。

### 三个要素

1. **时机**：`BEFORE`（事件之前）还是 `AFTER`（事件之后）
2. **事件**：`INSERT` / `UPDATE` / `DELETE`
3. **粒度**：`FOR EACH ROW`（每影响一行就触发一次）——MySQL 只支持行级

## 单元二：创建触发器的语法

```sql
CREATE TRIGGER 触发器名
AFTER INSERT ON 借阅
FOR EACH ROW
BEGIN
  -- 要自动做的事
END;
```

**逐词**：
- `CREATE TRIGGER 名字` —— 创建触发器
- `AFTER INSERT ON 借阅` —— 时机 + 事件 + 绑定的表
- `FOR EACH ROW` —— 每行触发一次
- `BEGIN ... END` —— 触发器体，可写多条 SQL

删除：

```sql
DROP TRIGGER IF EXISTS 触发器名;
```

查看：

```sql
SHOW TRIGGERS;
```

### OLD 和 NEW——触发器里的"两个影子"

这是触发器最关键的概念：

| 事件 | `OLD.列` | `NEW.列` |
|---|---|---|
| **INSERT** | ❌ 没有旧行 | ✅ **正要插入的新行** |
| **UPDATE** | ✅ 改之前的旧值 | ✅ 改之后的新值 |
| **DELETE** | ✅ **正要删除的旧行** | ❌ 没有新行 |

**记忆**：**INSERT 只有 NEW（新来的）、DELETE 只有 OLD（要走的）、UPDATE 两个都有（改前改后）**。

⚠️ **一个关键能力**：在 **BEFORE** 触发器里，可以 `SET NEW.列 = ...` **修改即将写入的值**。这是"兜底/纠错"的常用手法。AFTER 触发器里改 NEW 没用（数据已经写进去了）。

## 单元三：三个典型用途（都有 SQL）

### 用途 1：审计日志——"谁动了数据，记一笔"

**需求**：每次往借阅表插入一条记录，自动写一条日志。

先建日志表：

```sql
CREATE TABLE 借阅日志 (
  日志号 INT AUTO_INCREMENT PRIMARY KEY,
  借阅号 INT,
  读者编号 CHAR(3),
  图书编号 CHAR(4),
  记录时间 DATETIME
);
```

再建触发器：

```sql
CREATE TRIGGER trg_借阅日志
AFTER INSERT ON 借阅
FOR EACH ROW
BEGIN
  INSERT INTO 借阅日志(借阅号, 读者编号, 图书编号, 记录时间)
  VALUES (NEW.借阅号, NEW.读者编号, NEW.图书编号, NOW());
END;
```

插入一条借阅后，日志表自动多一行（本机已实测）：

```
借阅号 | 读者编号 | 图书编号
10     | 004     | B002
```

**要点**：触发器里用 `NEW.借阅号` 拿到刚插入那一行的值。

### 用途 2：自动维护数据——"借了书，次数自动 +1"

**需求**：每次插入借阅记录，自动把该读者的借阅次数加 1。

```sql
CREATE TRIGGER trg_借阅次数
AFTER INSERT ON 借阅
FOR EACH ROW
BEGIN
  UPDATE 读者 SET 借阅次数 = 借阅次数 + 1
  WHERE 读者编号 = NEW.读者编号;
END;
```

实测：插入一条 004 的借阅，`读者.借阅次数` 从 2 变 3。

**注意**：这是**跨表操作**——触发器绑在借阅表，但改的是读者表。MySQL 允许。

### 用途 3：BEFORE 兜底——"脏数据进不来"

**需求**：插入图书时，如果馆藏量是负数，自动改成 0。

```sql
CREATE TRIGGER trg_馆藏兜底
BEFORE INSERT ON 图书
FOR EACH ROW
BEGIN
  IF NEW.馆藏量 < 0 THEN
    SET NEW.馆藏量 = 0;
  END IF;
END;
```

实测：插入 `馆藏量 = -5` 的书，最终存进去的是 **0**。

**为什么必须用 BEFORE**：要在**写入之前**改 `NEW` 的值；如果用 AFTER，数据已经写进表了，改 NEW 没用。

```sql
SHOW TRIGGERS;                       -- 看所有触发器
DROP TRIGGER IF EXISTS trg_借阅日志;  -- 删
```

⚠️ **触发器是"隐形的副作用"**：调试时如果发现数据莫名其妙变了，先 `SHOW TRIGGERS;` 看看是不是有触发器在搞鬼。

## 单元五：事务——要么全成功，要么全失败

### 先看一个真实问题

"借书"其实包含**两步**：

1. 往借阅表插入一条借阅记录
2. 把读者的借阅次数 +1

如果第 1 步成功了、第 2 步失败了（比如程序崩了），数据就不一致了：有借阅记录，但次数没加。

**事务**就是解决这个的：**把多步操作打包成一个整体，要么全做，要么全不做。**

### 三条命令

```sql
START TRANSACTION;   -- 开启事务
-- 一堆 SQL
COMMIT;              -- 提交：全部生效
-- 或者
ROLLBACK;            -- 回滚：全部撤销
```

**实测对比**（本机）：

```sql
START TRANSACTION;
INSERT INTO 图书 VALUES ('B098','事务测试','某社',1);
ROLLBACK;
-- 再查 B098：查不到（被撤销了）
```

```sql
START TRANSACTION;
INSERT INTO 图书 VALUES ('B098','事务测试','某社',1);
COMMIT;
-- 再查 B098：查得到（已生效）
```

### ACID——事务的四大特性（必背）

| 特性 | 英文 | 含义 | 一句话 |
|---|---|---|---|
| **原子性** | Atomicity | 全做或全不做 | 要么都成，要么都黄 |
| **一致性** | Consistency | 从一个合法状态到另一个合法状态 | 数据不能自相矛盾 |
| **隔离性** | Isolation | 并发事务互不干扰 | 你干你的，我看不到 |
| **持久性** | Durability | 提交后永久保存 | COMMIT 了就丢不了 |

**记忆口诀**：**原子全或全不、一致不乱、隔离不扰、持久不丢**。

⚠️ **考试爱考**：ACID 是哪四个、每个的中文名和含义。尤其"原子性"最常考。

## 单元六：封锁——并发控制的武器

### 为什么需要封锁

多个事务同时读写同一份数据，会出三类问题：

| 问题 | 现象 |
|---|---|
| **丢失修改** | 两个事务都改了同一数据，后改的覆盖了先改的 |
| **读脏数据** | 读到了另一个事务还没提交（可能回滚）的数据 |
| **不可重复读** | 同一事务内两次读同一数据，结果不一样（别人中途改了） |

### 两种锁

| 锁 | 又叫 | 作用 |
|---|---|---|
| **共享锁（S 锁）** | 读锁 | 加了 S 锁还能读，但**不能写** |
| **排他锁（X 锁）** | 写锁 | 加了 X 锁，**别人既不能读也不能写** |

**兼容性表**（背下来）：

| | S 锁 | X 锁 |
|---|---|---|
| **S 锁** | ✅ 兼容 | ❌ 不兼容 |
| **X 锁** | ❌ 不兼容 | ❌ 不兼容 |

**记忆**：**只有"读 + 读"能共存**（S-S 兼容），只要有一个要写（X），就得独占。

### 三级封锁协议（高频考点）

| 级别 | 做法 | 解决什么问题 |
|---|---|---|
| **一级** | 写前加 **X 锁**，**事务结束**释放 | **丢失修改** |
| **二级** | 一级 + 读前加 **S 锁**，**读完就释放** | 丢失修改 + **读脏数据** |
| **三级** | 一级 + 读前加 **S 锁**，**事务结束才释放** | 丢失修改 + 读脏 + **不可重复读** |

**记忆**：
- **一级管写**（X 锁）→ 防丢失修改
- **二级加读**（S 锁，读完放手）→ 再防读脏
- **三级读锁不放手**（事务结束才放）→ 再防不可重复读

**递进关系**：三级 ⊃ 二级 ⊃ 一级（越高级越严格）。

### 死锁

**死锁**：事务 A 持有锁 1、等锁 2；事务 B 持有锁 2、等锁 1 → 互相等，谁都动不了。

**解决**：
- 数据库**自动检测**死锁，选择一个事务**回滚**（牺牲一个，救活另一个）
- 预防：**按固定顺序申请锁**、一次申请所需全部锁
