# 一、判断题（10 题 × 1 分 = 10 分）

## 题 1

`A LEFT JOIN B` 之后，如果 `WHERE` 里写了 `B.某列 IS NOT NULL`，那么此时 `COUNT(*)` 与 `COUNT(B.某列)` 的结果相同。

<details><summary>👉 答案与解析</summary>

**对。**

`WHERE B.某列 IS NOT NULL` 已经把 LEFT JOIN 补出来的 NULL 行全部刷掉了，剩下的每一行该列都非 NULL，所以"数行"和"数非 NULL"结果一样。

**陷阱设计**：前三次你栽在"LEFT JOIN 后 `COUNT(*)` 多数了补 NULL 的行"。这题反过来问——只要你用 `WHERE` 把补 NULL 行清掉，`COUNT(*)` 就恢复正常了。考的是**你到底知不知道自己错在哪一步**。

</details>

---

## 题 2

`COUNT(DISTINCT 列)` 和 `COUNT(列)` 都会跳过 NULL。

<details><summary>👉 答案与解析</summary>

**对。**

两者都只数**非 NULL** 值。区别只是 `DISTINCT` 去重。所以 `COUNT(DISTINCT 列) ≤ COUNT(列)` 恒成立。

**陷阱设计**：很多人以为"DISTINCT 会把 NULL 当成一个值数进去"。不会。聚合函数（除 `COUNT(*)`）一律无视 NULL。

</details>

---

## 题 3

当子查询的结果里可能含 NULL 时，把 `NOT IN` 改写成 `NOT EXISTS`，可以得到正确结果。

<details><summary>👉 答案与解析</summary>

**对。**

`NOT EXISTS` 是**逐行判断"存不存在"**，不存在就为真，不受 NULL 干扰；`NOT IN` 则是 `x <> 每个值`，碰上 NULL 就变 UNKNOWN，整行被丢掉。

**陷阱设计**：这是 #23 的正面考法。记住修复手法：**子查询可能出 NULL → 不要用 NOT IN，用 NOT EXISTS 或 LEFT JOIN ... IS NULL。**

</details>

---

## 题 4

`AVG(列)` 在没有匹配行时返回 NULL，而 `COUNT(列)` 在没有匹配行时返回 0。

<details><summary>👉 答案与解析</summary>

**对。**

空集上：`COUNT` 返回 0；`SUM`、`AVG`、`MAX`、`MIN` 全部返回 NULL。

**陷阱设计**：别把 `COUNT` 的 0 推广到所有聚合函数。`SUM` 空集是 NULL 不是 0（#20 的根）。

</details>

---

## 题 5

在 `LEFT JOIN` 之后分组，`HAVING COUNT(*) > 1` 与 `HAVING COUNT(右表列) > 1` 对同一查询的结果一定相同。

<details><summary>👉 答案与解析</summary>

**错。**

左表中**完全没有匹配**的行，右表列是 NULL：`COUNT(*)` 算它 **1**，`COUNT(右表列)` 算它 **0**。当阈值是 `> 1` 时，这一行两种写法都不入选，看起来一样；但只要阈值是 `>= 1`，差别立刻出现。

**陷阱设计**："一定相同"四个字就是钩子。本卷题 21 会用真实数据让你看到两者选出的人不一样。

</details>

---

## 题 6

M:N 联系转换成关系表时，主码必须是两端实体主码的组合，不能再加入其他属性。

<details><summary>👉 答案与解析</summary>

**错。**

如果同一对实体之间可以发生**多次**联系（同一客户多次租同一辆车、同一教师多学期教同一门课），两端主码组合会重复，必须加入能**区分每次联系**的属性（取车时间、授课学期）才能唯一标识一行。

**陷阱设计**：直接复现 #24。上次你在"授课表"漏了授课学期，这次换成"租赁表"的取车时间——同一个坑，换个业务。

</details>

## 题 7

同一张表上可以建多个 `UNIQUE` 约束，且 `UNIQUE` 列允许出现多个 NULL。

<details><summary>👉 答案与解析</summary>

**对。**

MySQL 的 `UNIQUE` 只约束**非 NULL** 值：多个 NULL 不算重复。所以"门店.员工号 UNIQUE"可以有多家门店暂时没有店长（员工号为 NULL）。

**陷阱设计**：很多人把 UNIQUE 当成"不许为空"。UNIQUE 完全允许 NULL，而且允许多个。这一点和主键相反。

</details>

## 题 8

MySQL 支持 `SELECT * FROM A FULL OUTER JOIN B ON ...` 这种写法。

<details><summary>👉 答案与解析</summary>

**错。**

MySQL **没有** `FULL OUTER JOIN` 语法（实测报 1064 语法错误）。要用：

```sql
SELECT ... FROM A LEFT JOIN B ON ...
UNION
SELECT ... FROM A RIGHT JOIN B ON ...;
```

**陷阱设计**：教材讲关系代数时"全外连接"是标准运算，但 MySQL 不实现这个关键字。**概念上有 ≠ SQL 里有。**

</details>

## 题 9

在 `READ COMMITTED` 隔离级别下，同一个事务内两次读取同一行，必然得到相同的值。

<details><summary>👉 答案与解析</summary>

**错。**

`READ COMMITTED` 只保证"不读脏数据"，**不保证可重复读**：两次读之间别的事务可以提交修改，第二次就读到新值——这叫**不可重复读**。

要保证同一事务内两次读一致，需要 `REPEATABLE READ`（MySQL 默认级别）。

**陷阱设计**：把"读已提交"误当成"读了就不变"。级别越高约束越强：RU < RC < RR < SERIALIZABLE。

</details>

## 题 10

HDFS 采用主从结构：`NameNode` 管理元数据，`DataNode` 存储实际数据块。

<details><summary>👉 答案与解析</summary>

**对。**

NameNode 记"文件被切成哪些块、每块在哪几个 DataNode 上"；DataNode 真正存块。`SecondaryNameNode` 只帮忙合并 FsImage 和 EditLog，不是热备。

## 题 11【数据推演 · COUNT(*)】

```sql
SELECT 姓名, COUNT(*) AS 订票数
FROM 乘客 LEFT JOIN 订票 ON 乘客.身份证号 = 订票.身份证号
GROUP BY 乘客.身份证号, 乘客.姓名;
```

赵六的"订票数"是（ ）。

A. 0　B. 1　C. 2　D. NULL

<details><summary>👉 答案与解析</summary>

**B（1）。**

赵六没有任何订单，LEFT JOIN 给他补了一行（订单号、航班号、票价全是 NULL）。`COUNT(*)` 数的是**行**，这一行照数 → **1**。

> 这就是 #4 的原始形态。先看清楚它错成什么样。

</details>

## 题 12【数据推演 · COUNT(列)】

同一查询，把 `COUNT(*)` 换成 `COUNT(订票.订单号)`，赵六的值是（ ）。

A. 0　B. 1　C. 2　D. NULL

<details><summary>👉 答案与解析</summary>

**A（0）。**

`COUNT(列)` 只数**非 NULL**。赵六那行的订单号是 NULL → 不数 → 0。

**这才叫"没订过票"的正确表达。**

</details>

## 题 13【数据推演 · NULL 不数】

用 `COUNT(订票.票价)` 统计，**李四**的值是（ ）。

A. 0　B. 2　C. 1　D. 3

<details><summary>👉 答案与解析</summary>

李四有两张订单：T3 票价 900、T5 票价 NULL。`COUNT(票价)` 只数 900 那一张 → **1**。

> 同一行数据，`COUNT(*)` 得 2、`COUNT(订单号)` 得 2、`COUNT(票价)` 得 1。**三个数字，三种含义。**

</details>

用 `SUM(订票.票价)` 统计，**周九**的值是（ ）。

## 题 15【反推 SQL · 含 0 的分组】

要得到下面这个结果：

| 航班号 | 订票数 |
|---|---|
| CA101 | 2 |
| CA102 | 1 |
| CA103 | 2 |
| CA104 | 1 |
| CA105 | **0** |

应选（ ）。

A. `SELECT 航班号, COUNT(*) FROM 航班 INNER JOIN 订票 ON ... GROUP BY 航班号;`
B. `SELECT 航班.航班号, COUNT(订票.订单号) FROM 航班 LEFT JOIN 订票 ON ... GROUP BY 航班.航班号;`
C. `SELECT 航班.航班号, COUNT(*) FROM 航班 LEFT JOIN 订票 ON ... GROUP BY 航班.航班号;`
D. `SELECT 航班.航班号, COUNT(订票.订单号) FROM 订票 LEFT JOIN 航班 ON ... GROUP BY 航班.航班号;`

<details><summary>👉 答案与解析</summary>

**B。**

- A：`INNER JOIN` → CA105 直接消失，不会出现 0。
- C：`LEFT JOIN` 对 → 但 `COUNT(*)` 把 CA105 的补 NULL 行数成 1。
- D：左表搞反了，以订票为主表 → CA105 消失。
- **B：保留全部航班（LEFT JOIN），且只数真实的订单号（COUNT(订票.订单号)）→ 0 正确。**

**一句话：LEFT JOIN 配 `COUNT(右表列)`，缺一不可。**

</details>

## 题 16【反推 SQL · 从未订过】

要查出**从未被订过票的航班**（结果应只有 CA105），应选（ ）。

A. `SELECT 航班号 FROM 航班 WHERE 航班号 NOT IN (SELECT 航班号 FROM 订票);`
B. `SELECT 航班号 FROM 航班 WHERE 航班号 IN (SELECT 航班号 FROM 订票);`
C. `SELECT 航班号 FROM 航班 WHERE NOT EXISTS (SELECT 1 FROM 订票 WHERE 订票.航班号 = 航班.航班号);`
D. `SELECT 航班号 FROM 航班 WHERE 航班号 <> ALL (SELECT 航班号 FROM 订票);`

<details><summary>👉 答案与解析</summary>

**C。**

子查询 `SELECT 航班号 FROM 订票` 里有 **NULL**（T6 的航班号）。于是：

- A、D（`<> ALL` 等价于 `NOT IN`）：每一行都要和 NULL 比较 → UNKNOWN → **0 行**，CA105 也查不出来。
- B：方向反了，查出的是"被订过的航班"（CA101~CA104）。
- **C：`NOT EXISTS` 逐行判断存在性，NULL-safe → 正确返回 CA105。**

**这是 #23 的换皮考法。看到"没有/从未" + 子查询可能含 NULL，条件反射写 NOT EXISTS。**

</details>

## 题 17【结果推演 · NOT IN 遇 NULL】

执行：

```sql
SELECT 航班号 FROM 航班
WHERE 航班号 NOT IN (SELECT 航班号 FROM 订票);
```

返回（ ）行。

A. 0　B. 1　C. 4　D. 5

<details><summary>👉 答案与解析</summary>

**A（0 行）。**

展开就是：`航班号 <> 'CA101' AND 航班号 <> 'CA102' AND ... AND 航班号 <> NULL`。

最后一项 `<> NULL` 是 **UNKNOWN**，`AND` 里只要有一个 UNKNOWN 且没有 FALSE，整个条件就不成立 → **一行都筛不出**。

**注意：结果为空 ≠ 没有符合条件的行。** 这次是 NULL 把条件毁了。

</details>

## 题 18【补全 SQL · NULL 比较】

要找出票价为 NULL 的订票记录，`WHERE` 子句应写（ ）。

A. `票价 = NULL`
B. `票价 == NULL`
C. `票价 <> NULL`
D. `票价 IS NULL`

<details><summary>👉 答案与解析</summary>

**D。**

NULL 表示"未知"，任何 `= NULL` / `<> NULL` 的结果都是 UNKNOWN，永远筛不出行（实测 `WHERE 票价 = NULL` 返回 0 行，`IS NULL` 返回 3 行）。

**判断空值只能用 `IS NULL` / `IS NOT NULL`。**

</details>

## 题 19【补全 SQL · 空组兜底】

统计每位乘客的订票总金额，**没订过票的显示 0**。SELECT 列表应写（ ）。

A. `IFNULL(SUM(订票.票价), 0) AS 总金额`
B. `SUM(订票.票价) AS 总金额`
C. `COUNT(订票.票价) AS 总金额`
D. `SUM(订票.订单号) AS 总金额`

<details><summary>👉 答案与解析</summary>

**A。**

- B：赵六、周九没有可加的值 → 显示 **NULL**（#20 复发点）。
- C：数出来的是"有几张有价的票"，不是金额。

</details>

## 题 20【补全 SQL · ON vs WHERE】

统计每位乘客**票价 ≥ 1000 的订票数**，**没订过票的也要显示 0**。正确写法是（ ）。

A. `FROM 乘客 LEFT JOIN 订票 ON 乘客.身份证号=订票.身份证号 AND 订票.票价>=1000`，`COUNT(订票.订单号)`
B. `FROM 乘客 LEFT JOIN 订票 ON 乘客.身份证号=订票.身份证号`，`WHERE 订票.票价>=1000`，`COUNT(订票.订单号)`
C. `FROM 乘客 LEFT JOIN 订票 ON 乘客.身份证号=订票.身份证号 AND 订票.票价>=1000`，`COUNT(*)`
D. `FROM 乘客 INNER JOIN 订票 ON 乘客.身份证号=订票.身份证号 AND 订票.票价>=1000`，`COUNT(*)`

<details><summary>👉 答案与解析</summary>

**A。**

- B：条件写 `WHERE` → 连接完再过滤，补 NULL 行全被刷掉 → 退化成内连接，赵六/周九直接消失。
- C：条件位置对，但用了 `COUNT(*)` → 没高价票的人被补一行 NULL，数成 **1**（李四、赵六、周九全错）。
- D：内连接，没票的人消失。
- **A：条件放 `ON` 保留左表全部行，`COUNT(右表列)` 数真实订单。**

正确结果：张三 1、李四 0、王五 1、赵六 0、周九 0。

**这是本卷最值钱的一题：ON/WHERE 的位置 × COUNT(*)/COUNT(列) 的组合。两个都选对才得分。**

</details>

## 题 21【补全 SQL · HAVING 辨析】

要找出"**至少订过一张票**"的乘客（含未定价订单；赵六没订过，不能出现）。分组后应写（ ）。

A. `HAVING COUNT(*) >= 1`
B. `HAVING COUNT(订票.票价) >= 1`
C. `HAVING COUNT(订票.订单号) >= 1`
D. `HAVING SUM(订票.票价) >= 1`

<details><summary>👉 答案与解析</summary>

**C。**

在 `乘客 LEFT JOIN 订票` 下：

- A：赵六有一行补 NULL 的记录 → `COUNT(*) = 1` → **赵六被错误选入**。
- B：周九只有票价为 NULL 的订单 → `COUNT(票价) = 0` → **周九被错误排除**。
- D：周九 `SUM(票价) = NULL`，`NULL >= 1` 是 UNKNOWN → 周九也被排除。
- **C：`COUNT(订票.订单号)` 数的是真实订单 → 张三、李四、王五、周九，正好。**

**核心：判断"有没有记录"要数明细表的主码列，不要数 `*`，更不要数可能为空的业务列。**

</details>

## 题 22【补全 SQL · SUM(CASE)】

要**同时**输出每位乘客的"订单总数"和"高价订单数（票价 ≥ 1000）"，没订票的显示 0。"高价订单数"这一列应写（ ）。

A. `COUNT(订票.票价 >= 1000)`
B. `COUNT(订票.票价)`
C. `SUM(订票.票价) / 1000`
D. `SUM(CASE WHEN 订票.票价 >= 1000 THEN 1 ELSE 0 END)`

<details><summary>👉 答案与解析</summary>

**D。**

- A：`COUNT(表达式)` 数的是"表达式非 NULL 的行"。`票价 >= 1000` 为**假**时结果是 0，**0 不是 NULL，照样被数**！所以张三会被数成 2（一张 1200 真、一张 800 假），错。
- B：数的是有价的票，不是高价票。
- C：金额除以 1000，毫无意义。
- **D：满足记 1、不满足记 0，`SUM` 才是"计数 + 条件"的唯一正确姿势。空组也得 0（ELSE 0 兜底）。**

正确结果：张三 1、李四 0、王五 1、赵六 0、周九 0。

> 记忆：**`COUNT(条件)` 是陷阱，`SUM(CASE...)` 才是答案。**

</details>

## 题 23【关系代数 · 差】

"**没有订过任何票的乘客**"，用关系代数最直接的运算是（ ）。

A. 并　B. 差　C. 交　D. 除

<details><summary>👉 答案与解析</summary>

**B（差）。**

`π(乘客) − π(订票)`：全体乘客减去订过票的乘客 = 没订过的。

- "至少订过一种" → 并
- "两种都订了" → 交
- "全部航班都订了" → 除
- "**没有**做某事" → 差

</details>

## 题 24【范式 · 传递依赖】

关系 `R(订单号, 身份证号, 姓名)`，函数依赖：`订单号 → 身份证号`、`身份证号 → 姓名`。

A. 订单号；2NF
B. 订单号；3NF
C. (订单号, 身份证号)；2NF
D. 身份证号；3NF

<details><summary>👉 答案与解析</summary>

**A。**

- 候选键：`订单号` 能定全表；单个属性，最简 → 候选键。

**拆法**：`订单(订单号, 身份证号)` + `乘客(身份证号, 姓名)`。

## 题 41（10 分）综合设计（汽车租赁）

**需求描述**：

> 杭州一家汽车租赁公司要建管理系统。公司有多家**门店**，每家门店有编号、名称和地址；公司要求每家门店必须指定一名**店长**，店长从公司**员工**中产生，一名员工最多只能担任一家门店的店长；员工有员工号、姓名、职务。门店里的**车辆**都要登记：车牌号、品牌、日租金、座位数；每辆车只归属一家门店（即使偶尔跨店调车，系统也只记录它当前的归属门店）。来租车的**客户**需要登记客户号、姓名、手机号和驾照号；同一位客户可以反复租用同一辆车，每次租车都要记录取车时间；如果还没还车，还车时间先留空，还车后再补上。市场部还希望记录客户的"消费等级"（由累计消费金额自动算出），这个等级不进入数据库。

**要求**：

1. （3 分）找出实体、属性和联系，指出**三个联系**各自的类型及理由
2. （4 分）转换为关系模式，标出主码和外码（1:1 联系请说明你放在哪一端）
3. （3 分）写出创建"**租赁**"表的 SQL（复合主键 + 两个外键）

<details><summary>👉 答案与解析</summary>

**1. 实体、属性、联系（3 分）**

- 实体：门店(<u>门店号</u>, 门店名, 地址)、员工(<u>员工号</u>, 姓名, 职务)、车辆(<u>车牌号</u>, 品牌, 日租金, 座位数)、客户(<u>客户号</u>, 姓名, 手机号, 驾照号)
- 联系：
  - **归属**：车辆 N — 1 门店（多辆车属一门店，一车只属一门店）
  - **租赁**：客户 M — N 车辆（一客户可租多车、可多次租同一车；一车也可被多客户先后租），联系属性：**取车时间、还车时间**
  - **担任店长**：员工 1 — 1 门店（一店一名店长，一名员工最多担任一家门店的店长）

> 干扰信息：①"偶尔跨店调车"——系统只记当前归属，**不建调车表**；②"消费等级不进入数据库"——**不要给它建属性**。

**2. 关系模式（4 分）**

```
员工( 员工号, 姓名, 职务 )
门店( 门店号, 门店名, 地址, 员工号 )        ← 担任店长 1:1，合并到门店端
      员工号 NOT NULL UNIQUE，外码：员工号 → 员工
车辆( 车牌号, 品牌, 日租金, 座位数, 门店号 )  ← 归属 1:N，外码：门店号 → 门店
客户( 客户号, 姓名, 手机号, 驾照号 )
租赁( 客户号, 车牌号, 取车时间, 还车时间 )    ← 租赁 M:N
      主码 = (客户号, 车牌号, 取车时间)
      外码：客户号 → 客户；车牌号 → 车辆
```

> 1:1 也可以反过来把"门店号"放进员工表，两种都算对，但**必须说明放哪端**。放门店端的理由是"每家门店必须有一名店长"，把外码放门店端、且加 `UNIQUE`，才能表达"一店一店长"。

**3. 建表 SQL（3 分）**

```sql
CREATE TABLE 租赁 (
  客户号   CHAR(3)  NOT NULL,
  车牌号   CHAR(7)  NOT NULL,
  取车时间 DATETIME NOT NULL,
  还车时间 DATETIME NULL,
  PRIMARY KEY (客户号, 车牌号, 取车时间),
  FOREIGN KEY (客户号) REFERENCES 客户(客户号),
  FOREIGN KEY (车牌号) REFERENCES 车辆(车牌号)
);
```

**陷阱点（三个，逐个对照）**：

1. **主码必须带"取车时间"**。同一客户可以多次租同一辆车，只写 `(客户号, 车牌号)` 第二次就插不进去——#24 的同一个坑。
2. **还车时间必须允许 NULL**。未还车时它就是 NULL；写成 `NOT NULL` 业务立刻卡死。
3. **1:1 的外码要加 `UNIQUE NOT NULL`**：`UNIQUE` 防止一个员工当多家店长（否则退化成 1:N），`NOT NULL` 落实"每家门店必须有一名店长"。

</details>

## 题 42（10 分）诊断 + 写查询（电商售后）

**场景**：

|---|---|---|

| P2 | 键盘 | 299 |

订单：

|---|---|---|
| O1 | P1 | 2 |

**要求**：

1. （2 分）查询每个商品的**订单数**，从未售出的显示 **0**
2. （3 分）查询每个商品的**评价条数**和**有效评分数**（评分非 NULL）各一列
3. （2 分）查询**至少有一条有效评分**的商品（写出 SQL，并说明用 `HAVING COUNT(*) >= 1` 会错在哪）
4. （3 分）查询每个商品**评分 ≥ 4 的评价条数**，没有的显示 0

<details><summary>👉 答案与解析</summary>

**1. 每个商品的订单数（2 分）**

```sql
SELECT 商品.商品号, 商品.商品名, COUNT(订单.订单号) AS 订单数
FROM 商品 LEFT JOIN 订单 ON 商品.商品号 = 订单.商品号
GROUP BY 商品.商品号, 商品.商品名
ORDER BY 商品.商品号;
```

真实结果：

| 商品号 | 订单数 |
|---|---|
| P1 | 2 |
| P2 | 2 |
| P3 | **0** |

**2. 评价条数与有效评分数（3 分）**

```sql
SELECT 商品.商品号,
       COUNT(评价.评价号) AS 评价数,
       COUNT(评价.评分)   AS 有效评分数
FROM 商品
LEFT JOIN 订单 ON 商品.商品号 = 订单.商品号
LEFT JOIN 评价 ON 订单.订单号 = 评价.订单号
GROUP BY 商品.商品号
ORDER BY 商品.商品号;
```

真实结果：

| 商品号 | 评价数 | 有效评分数 |
|---|---|---|
| P1 | 2 | **1** |
| P2 | 2 | 2 |
| P3 | 0 | 0 |

P1 有 E1(5) 和 E2(NULL)：`COUNT(评价号)` 数 2 条评价，`COUNT(评分)` 只数 1 条有效分。

**3. 至少有一条有效评分的商品（2 分）**

```sql
SELECT 商品.商品号
FROM 商品
LEFT JOIN 订单 ON 商品.商品号 = 订单.商品号
LEFT JOIN 评价 ON 订单.订单号 = 评价.订单号
GROUP BY 商品.商品号
HAVING COUNT(评价.评分) >= 1;
```

结果：**P1、P2**。

如果用 `HAVING COUNT(*) >= 1`：P3 因为 LEFT JOIN 补了一行 NULL，`COUNT(*) = 1`，会被**错误选入**，结果变成 P1、P2、P3。

**4. 评分 ≥ 4 的评价条数（3 分）**

```sql
SELECT 商品.商品号,
       SUM(CASE WHEN 评价.评分 >= 4 THEN 1 ELSE 0 END) AS 高分评价数
FROM 商品
LEFT JOIN 订单 ON 商品.商品号 = 订单.商品号
LEFT JOIN 评价 ON 订单.订单号 = 评价.订单号
GROUP BY 商品.商品号
ORDER BY 商品.商品号;
```

真实结果：

| 商品号 | 高分评价数 |
|---|---|
| P1 | 1 |
| P2 | **1** |
| P3 | 0 |

**两个常见错误写法**：

- `COUNT(评价.评分 >= 4)`：P2 会得 **2**——因为 2 ≥ 4 为**假**，假值 0 不是 NULL，也被数进去。
- 把 `WHERE 评价.评分 >= 4` 写在连接后：P3 直接消失（不只是显示 0），LEFT JOIN 退化成内连接。

**评分要点**：第 1 问必须 `COUNT(订单.订单号)`；第 2 问必须区分 `COUNT(评价号)` 与 `COUNT(评分)`；第 3 问必须 `COUNT(评分)` 而不是 `COUNT(*)`；第 4 问必须 `SUM(CASE)` 且 `ELSE 0`。

| A3 | C2 | **NULL** |
| A4 | C3 | 3000 |
| A5 | **NULL** | 800 |

> A5 是"待认领账户"，还没有归属储户；A3 已开户但余额未初始化。

**要求**：

1. （2 分）查询每个储户的**账户数**，没有账户的显示 **0**
2. （2 分）查询每个储户的**余额合计**，没有账户或余额全为 NULL 的显示 **0**
3. （3 分）查询**没有账户的储户**：
   - 先用 `NOT IN` 写，说明实际返回什么、为什么
   - 再写出正确写法
4. （3 分）对整个账户表，`COUNT(*)`、`COUNT(余额)`、`SUM(余额)`、`AVG(余额)` 各是多少？

<details><summary>👉 答案与解析</summary>

**1. 账户数（2 分）**

```sql
SELECT 储户.储户号, 储户.储户名, COUNT(账户.账号) AS 账户数
FROM 储户 LEFT JOIN 账户 ON 储户.储户号 = 账户.储户号
GROUP BY 储户.储户号, 储户.储户名
ORDER BY 储户.储户号;
```

| 储户号 | 账户数 |
|---|---|
| C1 | 2 |
| C2 | 1 |
| C3 | 1 |
| C4 | **0** |

若用 `COUNT(*)`，C4 会显示 **1**。

**2. 余额合计（2 分）**

```sql
SELECT 储户.储户号, 储户.储户名, IFNULL(SUM(账户.余额), 0) AS 余额合计
FROM 储户 LEFT JOIN 账户 ON 储户.储户号 = 账户.储户号
GROUP BY 储户.储户号, 储户.储户名
ORDER BY 储户.储户号;
```

| 储户号 | 余额合计 |
|---|---|
| C1 | 17000 |
| C2 | **0** |
| C3 | 3000 |
| C4 | **0** |

不加 `IFNULL` 时，C2 和 C4 都会显示 **NULL**（C2 唯一的账户余额是 NULL，C4 没有账户）。

**3. 没有账户的储户（3 分）**

错误写法（`NOT IN`）：

```sql
SELECT 储户号, 储户名 FROM 储户
WHERE 储户号 NOT IN (SELECT 储户号 FROM 账户);
```

**实际返回 0 行**（连真正没有账户的 C4 也查不出来）。

原因：子查询 `SELECT 储户号 FROM 账户` 的结果包含 **NULL**（A5 的储户号）。`NOT IN` 展开后要对每一行做 `储户号 <> NULL`，结果是 **UNKNOWN**，整个条件不成立。

正确写法（二选一）：

```sql
-- 写法一：NOT EXISTS
SELECT 储户号, 储户名 FROM 储户 c
WHERE NOT EXISTS (SELECT 1 FROM 账户 a WHERE a.储户号 = c.储户号);

-- 写法二：LEFT JOIN + IS NULL
SELECT 储户.储户号, 储户.储户名
FROM 储户 LEFT JOIN 账户 ON 储户.储户号 = 账户.储户号
WHERE 账户.账号 IS NULL;
```

结果：**C4（丁）**。

**4. 全表统计（3 分）**

```sql
SELECT COUNT(*) AS 行数, COUNT(余额) AS 非空余额数,
       SUM(余额) AS 合计, AVG(余额) AS 平均
FROM 账户;
```

| 行数 | 非空余额数 | 合计 | 平均 |
|---|---|---|---|
| 5 | 4 | 20800 | 5200 |

- `COUNT(*)` = 5：数行，NULL 行也数。
- `COUNT(余额)` = 4：跳过 A3 的 NULL。
- `SUM(余额)` = 5000 + 12000 + 3000 + 800 = **20800**：NULL 不参与加法。
- `AVG(余额)` = 20800 / **4** = **5200**：注意分母是 4 不是 5，NULL 连分母都不算。

**评分要点**：第 1 问 `COUNT(账户.账号)`；第 2 问 `IFNULL(SUM(...),0)`；第 3 问必须点出"子查询含 NULL → NOT IN 全毁"，并给出 NOT EXISTS；第 4 问四个数全对才给满分，尤其 AVG 的分母。

</details>
